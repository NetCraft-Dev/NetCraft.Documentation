# Справочник по NetCraft-ModApi

`NetCraft.ModApi` — это поверхность API, которую NetCraft предоставляет модам. У него две особенности: для вас это библиотека API; для себя это обычный мод (`id` есть `netcraft-modapi`, в поставке свои `ncmod.json` и щупы для впрыска).

Этот файл растет по мере роста API. Информацию об архитектуре, отличиях от Fabric и о том, как написать мод, см. в [modding-guide.md](modding-guide.md).

- Сборка: `NetCraft.ModApi.dll`

- Зависимости: `NetCraft` (основная библиотека), `NetCraft.Game`

Публичная поверхность разделена на три пространства имен:

| Пространство имен | Содержание | Заметки |
| --- | --- | --- |
| `NetCraft.ModApi.Wrapper` | Базовый класс событий и подписки `NcEvent<T>`, фасады `Nc*`, дескрипторы объектов `Nc*` | Оберточный слой; никаких типов ядра в открытом доступе |
| `NetCraft.ModApi.Extension` | Аннотации `[Inject]` / `[Mixin]` | Точки расширения; правила привязываются к именам классов и методов ядра |
| `NetCraft.ModApi.Internal` | Инъекционные зонды | Не ссылайтесь напрямую |

Корневое пространство имен `NetCraft.ModApi` содержит только класс записи `ModApiEntry`. `Wrapper` и `Extension` — два параллельных маршрута; о том, как выбрать, см. [modding-guide.md 2.9](modding-guide.md#29-two-routes-wrapper-layer-and-extension-points).

***

## 1. Быстрый старт

```csharp
using NetCraft.ModApi.Wrapper;

public sealed class MyModEntry
{
    public Task Init()
    {
        //subscription returns a handle; disposing it unregisters
        var handle = ServerEvents.Tick.Subscribe(args =>
            Log.Info($"tick {args.TickCount}"));

        ServerEvents.CommandRegister.Subscribe(args =>
            args.Register("mymod", "my mod command", builder =>
                builder.Executes(context =>
                {
                    context.GetSource().SendSuccess("hi");
                    handle.Dispose();          //you can also do something else with the handle
                    return 1;
                })));

        return Task.CompletedTask;
    }
}
```

В `ncmod.json` укажите `entry` на этот класс и оставьте `hooks` пустым — все события ниже предоставляются собственными зондами ModApi.

## 2. События

Все события живут под `NetCraft.ModApi.Wrapper`; после `using NetCraft.ModApi.Wrapper;` они доступны.

### 2.1 Сводная таблица

| Событие | Тип аргумента | Триггер | Сиде | Точка подключения ModApi |
| ------------------------------- | ---------------------- | --------------------------------------------------------- | ------ | -------------------------------------------------------- |
| `ServerEvents.Tick` | `ServerTickArgs` | каждый такт основного цикла сервера | сервер | `DedicatedServer::Tick` (Отметить) |
| `ServerEvents.Started` | `ServerPhaseArgs` | основной цикл запущен после печати `Done (x.xxxs)!` | сервер | `MinecraftServer::Run` (Отметить) |
| `ServerEvents.Stopping` | `ServerPhaseArgs` | сервер начинает отключаться; игроки вот-вот будут отключены | сервер | `DedicatedServer::Stop` (Отметить) |
| `ServerEvents.CommandRegister` | `CommandRegisterArgs` | все встроенные команды зарегистрированы | сервер | `EffectCommand::Register` сайт вызова (CallSite) |
| `ServerEvents.PlayerJoin` | `PlayerJoinArgs` | последовательность пакетов соединения отправлена ​​| сервер | `PlayerList::PlaceNewPlayer` сайт вызова (CallSite) |
| `ServerEvents.PlayerLeave` | `PlayerLeaveArgs` | игрок удален из онлайн-списка | сервер | `PlayerList::RemovePlayer` сайт вызова (CallSite) |
| `ServerEvents.PlayerDisconnect` | `PlayerDisconnectArgs` | отключить отправленный пакет и соединение закрыто | сервер | `ServerPlayer::Disconnect` сайт вызова (CallSite) |
| `ServerEvents.PlayerHurt` | `PlayerHurtArgs` | Фактически нанесенный урон | сервер | `PlayerList::HurtPlayer` сайт вызова (CallSite) |
| `ServerEvents.PlayerDeath` | `PlayerDeathArgs` | сразу после обнуления здоровья | сервер | `PlayerList::RespawnPlayer` сайт вызова (CallSite) |
| `ServerEvents.PlayerChat` | `PlayerChatArgs` | после трансляции чата | сервер | `ServerGamePacketListenerImpl::HandleChat` сайт вызова (CallSite) |
| `ServerEvents.ChunkLoaded` | `ChunkLoadedArgs` | фрагмент впервые попадает в память | сервер | `ServerChunkCache::set_ChunkLoaded` сайт назначения (CallSite) |
| `ServerEvents.ChunkUnloaded` | `ChunkUnloadedArgs` | кусок оставляет память | сервер | `ServerChunkCache::set_ChunkUnloaded` сайт назначения (CallSite) |
| `ServerEvents.ChunkSaved` | `ChunkSavedArgs` | снимок, сделанный до записи фрагмента на диск | сервер | `ServerChunkCache::set_ChunkSaveSink` сайт назначения (CallSite) |
| `ServerEvents.CommandExecuted` | `CommandExecutedArgs` | команда завершила выполнение; синтаксические ошибки и отказы в разрешении тоже учитываются | сервер | `CommandManager::Execute` (CallSite) |
| `ServerEvents.LevelTick` | `LevelTickArgs` | тик уровня, один раз за каждый загруженный уровень за тик | сервер | `PersistentServerLevel::Tick` (CallSite) |
| `ServerEvents.SavedDataSaving` | `SavedDataSavingArgs` | сохраненные данные записываются на диск, на один шаг позже, чем сохранение фрагмента | сервер | `SavedDataStorage::ScheduleSave` (CallSite) |
| `ServerEvents.BlockChanged` | `BlockChangedArgs` | состояние блока изменено, скоро будет синхронизировано с клиентами | сервер | `IBlockUpdateSink::BlockChanged` (CallSite) |
| `ServerEvents.BlockBroken` | `BlockBrokenArgs` | блок сломан; добыча игроком и самоуничтожение красного камня учитываются | сервер | `ServerBlockUpdates::BreakBlock` (CallSite) |
| `ServerEvents.ItemDropped` | `ItemDroppedArgs` | Появился объект выпавшего предмета, включая предметы для разбивания блоков и продукты для приготовления пищи | сервер | `ServerBlockUpdates::SpawnDrop` (CallSite) |
| `NetworkEvents.PacketReceived` | `PacketReceivedArgs` | каждый входящий пакет, поставленный в очередь обработчику, включая фазы установления связи и состояния | оба | `PacketProcessor::ScheduleIfPossible` и `HandleNow` (CallSite) |
| `ClientEvents.Tick` | `ClientTickArgs` | каждый такт основного цикла клиента | клиент | `MinecraftClient::Tick` (Отметить) |

Порядок событий игрока: смерть вложена в поток боли, поэтому `PlayerDeath` предшествует соответствующему `PlayerHurt`; `PlayerLeave` и `PlayerDisconnect` — это две разные вещи: первый означает удаление из онлайн-списка (даже после `/kick` он срабатывает только после разрыва соединения), второй означает само разрыв соединения, и оба не гарантированно появляются в парах.

### 2.2 Подписка и отмена регистрации

```csharp
IDisposable Subscribe(Action<T> handler)
```

- При подписке на одно и то же событие несколько раз уведомления доставляются в порядке подписки.

- Dispatch делает снимок списка обратных вызовов, поэтому подписка или отмена регистрации внутри обратного вызова не влияет на текущую отправку.

- Без отмены регистрации он остается в силе навсегда; моды не предоставляют механизма выгрузки, поэтому ручная отмена регистрации обычно не требуется.

### 2.3 Типы аргументов

**`ServerTickArgs`**

| Недвижимость | Тип | Заметки |
| ----------- | ------ | ------------------------------------ |
| `TickCount` | `long` | количество тиков с момента запуска, начиная с 1 |

Обратите внимание, что это учитывается самим ModApi, а не `TickCount` ядра.

**`ClientTickArgs`**

| Недвижимость | Тип | Заметки |
| ----------- | ------ | ------------------------------- |
| `TickCount` | `long` | то же, что и выше, рассчитывается независимо на стороне клиента |

**`ServerPhaseArgs`**

| Недвижимость | Тип | Заметки |
| -------- | -------- | ---------------------------- |
| `Phase` | `string` | имя фазы, `started` или `stopping` |

Поле дублирует само событие; он сохраняется, поэтому при регистрации можно использовать один единый формат.

**`CommandRegisterArgs`**

| Член | Тип | Заметки |
| ------------------------------------ | --------------------------------------- | ---------------- |
| `Dispatcher` | `CommandDispatcher<CommandSourceStack>` | диспетчер команд ядра |
| `Register(name, description, build)` | метод | зарегистрировать команду и записать ее в реестр, см. 3.1 |

**`PlayerJoinArgs`**

| Недвижимость | Тип | Заметки |
| ------------- | -------------- | ---------------------------------------------- |
| `Player` | `ServerPlayer` | игрок, который только что присоединился; уже отправленные пакеты соединения, состояние безопасно для чтения |
| `ProfileName` | `string` | имя игрока |

**`PlayerLeaveArgs`**

| Недвижимость | Тип | Заметки |
| --------- | -------------- | ------------------------------------- |
| `Player` | `ServerPlayer` | уходящий игрок, которого на данный момент больше нет в онлайн-списке |
| `Removed` | `bool` | действительно ли удалено; `false` при повторном удалении |

**`PlayerDisconnectArgs`**

| Недвижимость | Тип | Заметки |
| -------- | -------------- | ------------------------------------- |
| `Player` | `ServerPlayer` | отключенный игрок |
| `Reason` | `string` | причина отключения; обычный текст, если он задан как компонент |

Пакет отключения отправлен, и соединение закрыто; отправка пакетов этому плееру теперь не имеет эффекта.

**`PlayerHurtArgs`**

| Недвижимость | Тип | Заметки |
| ---------- | --------------- | -------------------------------------------- |
| `Player` | `ServerPlayer` | игрок, который пострадал |
| `Attacker` | `ServerPlayer?` | игрок, нанесший урон; `null` за ущерб окружающей среде и командованию |
| `Amount` | `float` | сумма ущерба на этот раз |

Не срабатывает во время кадров неуязвимости или после смерти (`Hurt` ядра возвращает `false`).

**`PlayerDeathArgs`**

| Недвижимость | Тип | Заметки |
| ---------- | --------------- | ------------------------------ |
| `Player` | `ServerPlayer` | игрок, который умер |
| `Attacker` | `ServerPlayer?` | убийца; `null` когда его нет |

Ядро сбрасывается сразу после того, как здоровье достигает нуля, поэтому, когда событие срабатывает, у игрока уже есть полное здоровье в точке возрождения; координаты и дроп на момент смерти недоступны.

**`PlayerChatArgs`**

| Недвижимость | Тип | Заметки |
| ------------ | -------- | -------------------- |
| `SenderName` | `string` | имя отправителя |
| `Message` | `string` | текстовое сообщение |

Это событие является **уведомлением только для чтения**: исходный метод уже передал сообщение, поэтому изменение `Message` здесь не имеет никакого эффекта.

**`ChunkLoadedArgs`** **/** **`ChunkUnloadedArgs`** **/** **`ChunkSavedArgs`**

Эти три события имеют одинаковую форму аргументов:

| Недвижимость | Тип | Заметки |
| -------- | ----- | ------------------ |
| `X` | `int` | координата фрагмента X |
| `Z` | `int` | координата фрагмента Z |

Самый простой способ ошибиться — это `ChunkSaved`: ядру требуется этот обратный вызов для **синхронного создания моментального снимка**, в то время как сериализация и запись на диск выполняются асинхронно самим ядром. Так что трудоемкая работа в этом колбеке напрямую замедляет выгрузку чанка, да и деструктивные операции (удаление блоков, изменение инвентаря) сюда тоже идти не должны — он лишь обещает момент снимка.

Когда `ChunkUnloaded` срабатывает, объекты блока уже очищены вместе с чанком; если вы хотите читать блоки, используйте `ChunkSaved` (который также не может получить доступ к блокам) или более раннюю точку.

**`CommandExecutedArgs`**

| Недвижимость | Тип | Заметки |
| --------- | ---------------------- | ------------------------------------- |
| `Command` | `string` | необработанный текст команды; команды чата не содержат косой черты в начале |
| `Result` | `int` | возвращаемое значение команды; 0 означает отказ или отказ |
| `Source` | `CommandSourceStack?` | источник команд; `null` на пути перегрузки игрока |
| `Player` | `ServerPlayer?` | игрок, отдавший команду; `null` при запуске с консоли |

Событие возникает **после** завершения команды; он не может изменить исполнение. Здесь также возникают синтаксические ошибки и отказы в разрешении; используйте `Result`, чтобы отличить их друг от друга. Команды, которые игрок отправляет из панели чата, проходят через перегрузку `Execute(ServerPlayer, string)`, при которой ядро ​​создает внутренний источник команд, поэтому в этом случае `Source` — это `null` и устанавливается только `Player`.

**`LevelTickArgs`**

| Недвижимость | Тип | Заметки |
| -------------- | ----------------------- | -------------------------------------------- |
| `Level` | `NcLevel` | уровень перешел на этот тик |
| `RunsNormally` | `bool` | нормально ли оно продвигалось; `false` во время `/tick freeze` |

Срабатывает один раз за каждый загруженный уровень за такт, поэтому многоуровневый мир получает несколько срабатываний за такт. Триггерная точка – после **завершения** уровня; это точка наблюдения, а не точка перехвата.

**`SavedDataSavingArgs`**

| Недвижимость | Тип | Заметки |
| --------- | ------------------- | --------------------------- |
| `Storage` | `SavedDataStorage` | таблица сохраненных данных сохраняется |

Это путь, отличный от `ServerEvents.ChunkSaved`: первый фрагмент только делает снимок и записывает асинхронно, тогда как этот срабатывает после завершения синхронной записи. Через него проходят мировое время, правила игры и данные о мировых границах.

**`BlockChangedArgs`**

| Недвижимость | Тип | Заметки |
| -------- | ------------ | --------------------------- |
| `Pos` | `BlockPos` | положение измененного блока |
| `State` | `BlockState` | состояние блока после изменения |

Состояние уже записано в чанк и скоро будет синхронизировано с клиентами, поэтому само изменение здесь изменить нельзя. Компоненты Redstone, изменяющие свое состояние в обратных вызовах поведения, также выходят по этому пути; он высокочастотный, поэтому не занимайтесь трудоемкой работой в колбеке.

**`BlockBrokenArgs`**

| Недвижимость | Тип | Заметки |
| -------- | --------------- | ------------------------------------------ |
| `Pos` | `BlockPos` | положение сломанного блока |
| `Player` | `ServerPlayer?` | прерыватель; `null` по неигровым причинам, таким как редстоун |

Срабатывает только тогда, когда блок действительно заменяется; пустые позиции и отклоненные перерывы не вызывают его. Эффекты разрыва и падения уже обработаны, поэтому то, что вы читаете в событии, является результатом.

**`ItemDroppedArgs`**

| Недвижимость | Тип | Заметки |
| -------- | ----------- | ----------------------- |
| `Pos` | `BlockPos` | где появился выпавший предмет |
| `Stack` | `ItemStack` | стек выпавших предметов |

Сюда проходят как капли для разбивания блоков, так и продукты для приготовления пищи на костре. Пустой стек элементов не порождает никакой сущности, поэтому нет события.

**`PacketReceivedArgs`**

| Недвижимость | Тип | Заметки |
| --------------- | -------- | ------------------------ |
| `Listener` | `object` | слушатель, получающий этот пакет |
| `Packet` | `object` | сам объект пакета |
| `IsServerbound` | `bool` | является ли это пакетом, привязанным к серверу |

Срабатывает для каждого входящего пакета, охватывая все четыре фазы: подтверждение связи, статус, конфигурация и воспроизведение. Пакеты движения приходят несколько раз за тик, поэтому не выполняйте трудоемкую работу в обратном вызове. Пакет уже декодирован в объект, но не перешел на бизнес-уровень; чтобы различать типы, проверьте `Packet` самостоятельно. Исходящие пакеты выходят за рамки этого события.

## 3. Точки расширения

### 3.1 Регистрация команд

Время — `ServerEvents.CommandRegister`. Не кэшируйте аргументы этого события; внутреннее дерево команд строится только один раз при запуске.

```csharp
public void Register(
    string name,                                          //command literal, without the slash
    string description,                                   //one-line description, shown in the /ncmapi ledger
    Action<LiteralArgumentBuilder<CommandSourceStack>> build);   //attach arguments and the executor
```

Полученный вами `build` является бригадным сборщиком ядра; записывайте аргументы, подкоманды и предикаты разрешений способом ядра:

```csharp
ServerEvents.CommandRegister.Subscribe(args =>
    args.Register("tpall", "teleport all players to the executor", builder =>
        builder
            .Requires(s => s.HasPermission(2))            //permission predicate
            .Executes(context => { /* ... */ return 1; })));
```

С аргументами:

```csharp
args.Register("heal", "heal the target players", builder =>
    builder.Requires(s => s.HasPermission(2))
        .Then(RequiredArgumentBuilder<CommandSourceStack, EntitySelector>
            .Argument("targets", EntityArgument.Players())
            .Executes(context =>
            {
                foreach (var player in EntityArgument.GetPlayers(context, "targets"))
                    player.Heal(20f);                     //illustrative
                return 1;
            })));
```

Ключевые моменты:

- Прямой вызов `args.Dispatcher.Register(...)` также устанавливает команду, но она не входит в реестр и `/ncmapi` не отображает ее. Используйте `args.Register`, если хотите, чтобы он был указан в списке.

- По умолчанию команды не имеют ограничений по разрешению; добавьте `.Requires(...)` самостоятельно, если необходимо.

- Поведение во время выполнения полностью зависит от вас; ModApi его не перехватывает.

### 3.2 Просмотр зарегистрированных команд

Существует встроенный `/ncmapi`, требующий уровня разрешений 2:

```
/ncmapi
Commands registered via NetCraft-ModApi: 2 total
/ncmapi  list commands registered via NetCraft-ModApi
  /ncmapi
/tpall  teleport all players to the executor
  /tpall
/heal  heal the target players
  /heal <targets>
```

Строки использования вычисляются «на лету» из структуры узлов дерева команд: литералы записываются по имени, аргументы заключаются в угловые скобки, а промежуточные узлы, которые сами являются исполняемыми, также получают свою собственную строку.

## 4. Серверные фасады

Все фасады в этой главе находятся под `NetCraft.ModApi.Wrapper`; после `using NetCraft.ModApi.Wrapper;` они доступны.

Фасады — это статические классы `Nc*`, которые объединяют возможности, разбросанные по ядру, в несколько точек входа. Экземпляр ядра захватывается зондом при запуске основного цикла; когда `NcServer.IsAvailable` имеет значение false, все, что ниже, выдает — используйте их только внутри обратных вызовов событий, а не из `Init`.

| Фасад | Цель |
| --- | --- |
| `NcServer` | экземпляр сервера, тикрейт, команды, отслеживание объектов, данные игрока, правила игры, трансляция, выполнение команд |
| `NcPlayers` | запросы и действия онлайн-игроков (кик, телепорт, здоровье, режим игры, разрешения) |
| `NcWorld` | чтение/запись и взлом блока Overworld, погода, время, граница, часы, звуки, события уровня; использует дескрипторы `NcLevel` для достижения других измерений, координаты — простые `x y z` ints |
| `NcRegistries` | встроенные реестры, просматриваемые по имени (блоки, предметы, жидкости, эффекты, биомы, частицы, сущности, блочные сущности) |
| `NcRecipes` | запросы рецептов (создание сетки, резка камня, кулинария; получение рецептов по идентификатору) |
| `NcLists` | списки и конфиг (белый список, опс, баны, `server.properties`) |
| `NcStartup` | аргументы запуска (нераспознанные ядром токены и подписка на основе имени) |

`NcPlayer` — это не статический фасад, а **дескриптор объекта**: `NcPlayers.All` / `Find` возвращают его, и `Player` / `Attacker` в событиях игрока также являются им. Дескрипторы доступны только для чтения и создаются зондами; моды не могут получить `ServerPlayer` ядра — первый якорь «нет типов ядра в публичном доступе». Один и тот же игрок ядра всегда сопоставляется с одним и тем же дескриптором, кэшируется внутри по слабой ссылке и автоматически аннулируется после выхода игрока из системы.

`NcLevel` имеет ту же форму для уровней. `NcWorld.Overworld` / `Nether` / `End` и `NcWorld.Get("minecraft:the_nether")` возвращают его, и `LevelTickArgs.Level` тоже является одним из них. Он содержит идентификатор измерения, время, погоду, высоту сборки, количество тиков и принудительную загрузку фрагментов; блочные операции остаются на `NcWorld` и принимают дескриптор плюс `x y z`. `BlockPos` никогда не появляется, поэтому dll мода не имеет ссылки на тип уровня ядра.

### 4.1 Реестры

`NcRegistries` предоставляет как целые таблицы, так и поиск по имени. Целые таблицы предназначены для итерации и поиска на основе тегов; поиск по имени предназначен для получения одного элемента:

```csharp
var stone = NcRegistries.FindState("minecraft:stone");     //block default state
var diamond = NcRegistries.FindItem("minecraft:diamond");
var over = NcRegistries.FindBiome("minecraft:plains");

//iterate the whole table
foreach (var id in NcRegistries.Blocks.KeySet)
    Log.Info(id.ToString());
```

Реестры собираются постепенно во время запуска, а моды загружаются до завершения сборки, поэтому не кэшируйте ничего, что было найдено в `Init` — сборка все еще продолжается, и кешированное значение будет нулевой ссылкой или устаревшим значением. В настоящее время `BuiltInRegistries.BootStrap` все еще является пустой реализацией; каждый реестр заполняется отдельно с помощью собственного Bootstrap, а реестры, управляемые данными (биомы, рецепты и т. д.), имеют очень мало записей до того, как будет подключена загрузка пакета данных.

### 4.2 Рецепты

`NcRecipes` поддерживается таблицей рецептов, загруженной из пакетов данных; `/reload` заменяет всю таблицу, поэтому не сохраняйте `RecipeHolder` при перезагрузках.

```csharp
if (NcRecipes.IsAvailable)
{
    var result = NcRecipes.Craft(input);                    //compute the output for a crafting grid
    var recipes = NcRecipes.StonecuttingFor(stack);         //stonecutting recipes available for this input
    var smelting = NcRecipes.CookingFor("smelting", stack); //look up by cooking type
    var byId = NcRecipes.Find("minecraft:oak_planks");      //fetch a recipe by id
}
```

## 5. Внутреннее устройство

Вам не нужен этот раздел для написания модов, но он может помочь при отладке.

### 5.1 Зонды

| Класс | Форма | Ответственность |
| -------------------------------------------------------- | ----------- | ----------------------------------------------------------- |
| `Internal.SignalProbe.OnSignal(string)` | Марк ×4 | все сигналы «что-то произошло» направляются в один метод, отправляемый на соответствующее событие с помощью `label` |
| `Internal.CommandProbe.OnCommandsReady(object)` | CallSite | заменяет вызов `EffectCommand::Register`; после восстановления исходного вызова срабатывает `CommandRegister` |
| `Internal.PlayerProbe.OnXxx(object, ...)` | CallSite ×6 | события игрока, один метод на каждую точку привязки; после восстановления исходного вызова публикует событие |
| `Internal.LevelProbe.OnChunkXxxAssigned(object, object)` | CallSite ×3 | события фрагмента, подключенные к сайтам назначения трех свойств обратного вызова `ServerChunkCache`; делегат-оболочка накладывается перед передачей управления обратно ядру |
| `Internal.BlockProbe.OnXxx(...)` | CallSite ×3 | блокировать события; прерывание и отбрасывание перехватчика `ServerBlockUpdates`, изменение состояния перехватывает метод интерфейса на `IBlockUpdateSink` |

Подпись `SignalProbe` принимает только `string`, а параметры `CommandProbe`, `PlayerProbe` и `LevelProbe` объявлены как `object` — это намеренно: во время сборки `Lead.Hook` разрешает подпись метода замены, и как только в ней появляется тип ядра, его разрешение вызывает раннюю сборку ядра, и внедрение пропускает ее окно. Типы ядра появляются только внутри тел методов, к тому времени код уже запущен.

Единственное, что не может быть `object` в сигнатуре, — это параметры типа значения и возвращаемые значения: `object` — это ссылка в стеке, а `float`/`bool` — значения, а несовпадение является недопустимым IL. Таким образом, `PlayerProbe.OnHurtPlayer` сохраняет `float` для суммы ущерба, а `OnRemovePlayer` и `OnHurtPlayer` сохраняют возвращаемые значения `bool`.

`BlockProbe` является расширением этого ограничения: позиция и состояние блока — это два типа значений `BlockPos`/`BlockState`, которые могут быть записаны в сигнатуру только как сами по себе. Эти два типа происходят из `NetCraft.Primitives` и `NetCraft.Registry`, ни один из которых не находится в списке внедрения, поэтому их разрешение во время сборки не приводит к досрочному перезаписи сборок.

### 5.2 Список точек подключения

ModApi `ncmod.json` содержит двадцать четыре правила, которые соответствуют таблице в 2.1 один к одному. Чтобы изменить точку подключения или добавить правило, отредактируйте этот файл; после редактирования пересобрать (это встроенный ресурс) и поместить полученную dll обратно в `mods/` — последнее уже сделано автоматически `DeployModToHosts` в `NetCraft.ModApi.csproj`, а отсутствие этого проявляется как то, что правила вообще не вступают в силу.

`CommandManager::Execute` имеет две перегрузки, которые используют одно правило. CallSite `Lead.Hook` сопоставляет сайты вызовов по «типу + имя метода», а не по списку параметров, и обе перегрузки принимают два параметра, поэтому зонд может принимать `object` в качестве первого параметра и отправлять по реальному типу.

Два правила `PacketProcessor` дополняют друг друга: пакеты фазы воспроизведения проходят через `ScheduleIfPossible` в очередь основного потока, а фазы установления связи и состояния проходят через `HandleNow` для немедленной обработки; любой данный пакет проходит только через один из них. При перехвате только первого варианта пропускаются фазы рукопожатия и состояния, которые легче всего проверить с помощью сценариев, поэтому во время отладки это легко ошибочно истолковать как «правило не вступило в силу».

Три правила фрагментов перехватывают **сайты назначения** трех свойств обратного вызова `ServerChunkCache`, а не сайты чтения. Причина в том, что эти три свойства являются одноадресными и уже заняты самим ядром на момент создания `PersistentServerLevel` (они вводят логику сохранения и очистки блочного объекта); прямое назначение мода переопределит копию ядра — выгрузки не сохранятся, объекты блокировки не будут очищены и вообще без ошибок. Перехват сайта назначения позволяет связать обратный вызов ядра и зонд в этот момент; назначение происходит только один раз, и каждый последующий триггер добавляет один уровень пересылки делегата.

`PlayerList::RespawnPlayer` является частным, поэтому зонд не может восстановить исходный вызов; этот проходит через отражение (вызывается один раз за смерть, поэтому накладные расходы незначительны). Это также оставляет возможность для выравнивания ядра: если в будущем для него будет добавлен `InternalsVisibleTo`, его можно будет заменить на прямой вызов.

### 5.3 Книга учета

`Internal.NcCommandRegistry` записывает команды, зарегистрированные через `args.Register`. Это всего лишь реестр, который не участвует в выполнении команд; сами команды устанавливаются в диспетчере ядра, поэтому даже если в реестре возникнут проблемы, команды все равно будут работать.

## 6. Будет добавлено

Ниже приведены точки перехвата, местоположения которых подтверждены, но еще не стали событиями (список был создан `__scan_mod_api.py` в корне репозитория):

| Направление | Точки крючка кандидата |
| ----------------- | ---------------------------------------------------------------------------- |
| Сущности | `ClientLevel::AddEntity`, `Entity::Die` |
| Мир | уровень загрузки и выгрузки, пакетная обработка фрагментов `ServerChunkCache` |
| Генерация местности | `ChunkGenerator::Generate` этапы для `ChunkStatus`, `WorldGenRegion::SetBlockState` |
| Выполнение команды | `CommandSourceStack::SendSuccess` / `SendFailure` (половина ответа, со множеством точек вызова) |
| Сеть | для каждого типа пакета `ServerGamePacketListenerImpl::HandleXxx` (в настоящее время только унифицированная точка входа) |

Указания уже выполнены: отметки уровня стали `ServerEvents.LevelTick`, сохранение сохраненных данных стало `ServerEvents.SavedDataSaving`, выполнение команд стало `ServerEvents.CommandExecuted`, а блоки стали `ServerEvents.BlockChanged` / `BlockBroken` / `ItemDropped`.

Привязка блочной ячейки к `SetBlock` не работает: она имеет два параметра по умолчанию, `notifyNeighbors` и `strict`, поэтому скомпилированные сайты вызовов принимают от 4 до 6 параметров, а поскольку CallSite сопоставляется по «типу + имя метода» без просмотра списка параметров, один метод замены не может обрабатывать все три формы стека. Вместо этого он перехватывает два места: перехваты синхронизации состояния `IBlockUpdateSink::BlockChanged` (единственный вызов интерфейса в `ServerLevel.SetBlock`, охватывающий каждое изменение с синхронизацией клиента), а также прерывание и удаление перехвата собственных методов `ServerBlockUpdates`.

Ячейка сущностей вызывает проблемы, поскольку `Entity` определена в `NetCraft.Registry`, которой нет в списке внедрения, поэтому сайты вызовов, нацеленные на нее, не могут быть перезаписаны. `ClientLevel::AddEntity` находится в клиентской сборке и выполним; событие смерти сначала требует решения, можно ли переписать `Registry`.

Для ячейки сети `HandleChat` уже давно существует, а `NetworkEvents.PacketReceived` обеспечивает единую точку входа, поэтому перехваты для каждого `HandleXxx` гораздо менее ценны; Добавлять стоит только сценарии, требующие детальной фильтрации по типу пакета.

Уровень загрузки и выгрузки не имеет точки сходимости на стороне NC: `DedicatedServer::CreateLevel` является частным, поэтому исходный вызов может быть восстановлен только путем отражения, например `PlayerList::RespawnPlayer`; путь разгрузки еще более разбросан. Для этого сначала определите, какими должны быть аргументы события.

Всем остальным нужны ссылки на объекты (экземпляры сущностей и т. д.), поэтому они должны использовать `CallSite`, а не `Mark`; если среди параметров появляется тип значения ядра, его можно записать в сигнатуру метода замены только как самого себя.

Список интерфейсных поверхностей (`__modapi_api.txt`, созданный `__scan_mod_api.py --api`), также был рассмотрен: записи, квалифицированные как точки входа возможностей, были собраны в фасады главы 4 по доменам, а остальные, которые не представлены, делятся на три категории — обработка протоколов и пакетов (`Network.Protocol.*`), рендеринг и модели (`Client.Render.*`), а также функции генерации ландшафта и плотности (`LevelGen.*`). Это внутренности ядра; их использование напрямую привязывает моды к деталям реализации, поэтому сначала в ядре необходимо открыть стабильный интерфейс.

На стороне сервера есть еще две вещи, не обернутые как фасады: экземпляр `ReloadableServerResources` зависает на `DedicatedServer`, а поскольку ModApi не ссылается на `NetCraft.Server`, для его упаковки требуется сначала открыть свойство базового класса ядра; `ChunkSender` и `ServerWorldBorderListener` — это внутренние потоки, которые не используются для модов.
